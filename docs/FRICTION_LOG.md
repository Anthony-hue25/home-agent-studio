# Friction log

Real friction encountered building and deploying this project during the hackathon submission window (September 2026), all from this project's own AWS CLI / ECS Express Gateway deployment work. Every entry below happened exactly as described, in this project, on this deployment -- none is a generic or hypothetical complaint.

## F1 -- Custom `aws login` authorization codes are invocation-scoped, not reusable

**Tool / service:** AWS CLI custom `login` command (`aws login --remote`)

**Environment:** Windows, AWS CLI with an organization-provided `login` subcommand for browser-based SSO

**Steps taken:** Ran `aws login --remote`, copied the authorization code from a browser tab opened in a separate context, pasted it into the prompt from a second, later invocation.

**Expected result:** The pasted authorization code would be accepted and complete sign-in.

**Actual result:** `aws: [ERROR]: Failed to decode the verification code.` -- each `aws login --remote` invocation mints its own fresh PKCE `state`/`code_challenge` pair; a code generated by one invocation cannot be redeemed by another, even seconds later.

**Severity:** Major (blocked all further AWS CLI use until diagnosed)

**Workaround:** Used `aws login` **without** `--remote` on the machine that actually has its own display and browser -- this opens a local callback server and browser tab and completes the code exchange automatically in the same invocation, with no manual copy/paste step at all.

**Outcome:** Reauthentication succeeded on the first attempt with the corrected approach.

**Actionable suggestion to Amazon:** Document explicitly, next to `--remote`, that authorization codes are single-invocation and non-transferable, and recommend the no-`--remote` flow as the default for any machine with its own browser.

## F2 -- `describe-express-gateway-service` requires `--service-arn`, not `--service-name`

**Tool / service:** AWS CLI, ECS Express Gateway commands

**Environment:** AWS CLI on Windows, deploying to an ECS Express Gateway service

**Steps taken:** Ran `aws ecs describe-express-gateway-service --service-name <name> ...` following the same flag pattern used successfully for an earlier `update-express-gateway-service` call.

**Expected result:** A service description, matching the update command's own flag naming.

**Actual result:** `ParamValidationError: the following arguments are required: --service-arn` -- the describe and update commands for the same resource type take differently-named identifying flags.

**Severity:** Minor

**Workaround:** Switched to `--service-arn arn:aws:ecs:...`.

**Actionable suggestion to Amazon:** Make the identifying-flag name consistent between `update-express-gateway-service` and `describe-express-gateway-service` (or accept both).

## F3 -- `describe-service-deployments` requires an IAM permission not granted by default developer policies

**Tool / service:** AWS CLI / IAM, `ecs:DescribeServiceDeployments`

**Environment:** A scoped developer IAM user set up specifically for this project's ECS deployments

**Steps taken:** Ran `aws ecs describe-service-deployments` to check the status of an in-progress rolling deployment.

**Expected result:** Deployment status returned, to confirm whether the new task revision was healthy before proceeding.

**Actual result:** `AccessDeniedException` -- the developer IAM user's policy did not include `ecs:DescribeServiceDeployments`.

**Severity:** Minor (a workaround existed; would be Major without one)

**Workaround:** Polled the service's own `/health` endpoint directly at a fixed interval instead of querying deployment status through the ECS API. The rolling deployment completed and stabilized within about 30-45 seconds on its own.

**Actionable suggestion to Amazon:** Either include `ecs:DescribeServiceDeployments` in commonly-recommended starter developer policies for ECS, or make the permission requirement clearer in the CLI's own error message (it currently gives no hint that this is a distinct, separately-grantable permission from general `ecs:Describe*` access).

## F4 -- `continue-service-deployment` requires `--hook-id` in current CLI, undocumented relative to earlier examples

**Tool / service:** AWS CLI, `aws ecs continue-service-deployment`

**Environment:** Same ECS Express Gateway deployment as F2/F3, using a command pattern that had worked in an earlier deployment on this same project

**Steps taken:** Ran `aws ecs continue-service-deployment --service <name> ...` to advance a rolling deployment that appeared to be waiting.

**Expected result:** The deployment would continue, matching the earlier, successful invocation of the same command on this project.

**Actual result:** `ParamValidationError: the following arguments are required: --hook-id` -- the current CLI version requires a hook ID that the earlier working invocation did not need.

**Severity:** Minor (the deployment resolved on its own before this needed to be pursued further)

**Workaround:** Did not pursue this path further; confirmed via `/health` polling that the deployment completed without manual intervention.

**Actionable suggestion to Amazon:** Version-note breaking CLI parameter changes for deployment-lifecycle commands like this one, since a working script from one project phase silently stopped working in a later phase with no changelog pointer in the error itself.

## F5 -- Rolling deployment briefly showed two simultaneous active configurations, with no clear signal whether manual intervention was needed

**Tool / service:** AWS ECS Express Gateway, service rollout status

**Environment:** Same ECS Express Gateway deployment as F2-F4

**Steps taken:** After pushing a new task definition revision, described the service mid-rollout to confirm the new revision was taking over.

**Expected result:** A single active configuration (or a clear "in progress, revision N replacing revision N-1" status) with an obvious signal for when it was safe to consider the rollout complete.

**Actual result:** The describe output showed two `activeConfigurations` entries simultaneously (old and new revision) with nothing in the response indicating whether this was normal mid-rollout behavior or a stuck deployment requiring `continue-service-deployment` (which itself hit the `--hook-id` issue in F4).

**Severity:** Minor (resolved itself)

**Workaround:** Polled `/health` directly at a fixed interval instead of relying on the ECS describe output to judge rollout health. The second configuration disappeared and the rollout reported healthy within roughly 30-45 seconds without any manual step.

**Actionable suggestion to Amazon:** Have `describe-express-gateway-service` (or its rollout-status equivalent) surface an explicit "this is normal, no action needed" versus "this is stuck, action needed" signal, rather than leaving that inference to the caller.
